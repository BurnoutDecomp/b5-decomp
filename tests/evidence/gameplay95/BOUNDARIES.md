# Gameplay95 regression scope

This hosted fixture tests production C001/C002 source slices. It does not establish native menu behavior or rendered-frame parity. All counts below are authored expectations pending hosted execution.

## Executed production code

- The 19 selected, unconditional assignments from `RaceCarEntityModule::Construct`, in their actual order and with their actual expressions. The declaration types come from the production header. Every field is edited before each of three calls. Header initializers are deliberately excluded from the projected owner because they cannot implement reset on a reused object.
- The complete contact draw region between the actual `lbIsWall` classification and wall-triangle recording. Its real flag accessor bodies, `DebugInterface` constructor/destructor/`GetRender`, typed `CgsPC::VmxFloat::MultiplyAdd`, `DebugRender::DrawTriangle`/`DrawSolidSphere`, actual event declarations and the real `VariableEventQueue<16384,16>` remain production code.
- The complete production `DebugRender::Dispatch3D` switch, including its actual queue iteration and clear. Selected replay reaches production immediate `DrawTriangle`, `DrawSolidTriangle`, `DrawSolidSphere`, `DrawSolidQuad`, `AddQuad`, `AddTriangle`, `AddVertex`, drawing/projection transitions, flush, `Begin`, and `End`. Production `Add3`, PI constants, CPU vertex layout, colour packing and math headers are retained.
- Actual production `CgsStrStream.cpp` and `RwRGBA.cpp` are compiled as additional sources through unchanged `fxgs_common.compile_and_run`. The old log-only gate has a genuine engine stream sink; it is not replaced with a successful draw implementation.

## Explicit hosted boundaries

1. **Whole vehicle lifecycle:** the approximately 100 KiB racecar owner and its scene/resource/physics services are not constructed. `ResetOwner::Construct` is a projection of exact selected top-level production statements into the same typed named fields. This establishes those statements' reset behavior, not whole-Construct ordering, layout, object lifetime, consumers or engine integration. The comment-only D001 file is bound to its reviewed bytes but has no independent behavior check.
2. **Collision input:** the valid `Triangle4::AOSTriangle` uses its real declaration. Cache lookup, collision generation and height/classification math are not executed. The inputs supply the three valid mutually exclusive classifications (neither, wall, curb) and all four flag combinations. This fixture does not change game prerequisites or set native state.
3. **Manager/thread service:** the production interface definitions acquire/release an explicit hosted owner containing one actual `DebugRender`. The manager service records acquire/release balance. Production singleton initialization, critical-section implementation, cross-thread contention and actual manager layout are outside this fixture.
4. **Im3d submission:** the complete selected production immediate path submits copied CPU vertex batches to a typed observable endpoint with the called Im3d API signatures. This endpoint records state-call order, Begin/End, topology and the actual CPU vertices. It does not replace a selected Draw method. Production ImRenderBuffer command encoding/double-bank dispatch, state-resource construction, CPU32-to-GPU24 packing, shaders, D3D9/device operations and framebuffer pixels are not certified here. Existing PCIm3dBuffer and native rendering checks remain separate evidence.
5. **Unselected primitives:** methods referenced by other arms of the complete replay switch are fail-observable boundaries. Any invocation increments an unexpected-call count and fails `replay.clear_clean`. They never emit substitute geometry or satisfy a selected effect.
6. **Math limits:** the normal/vertices are finite exactly representable test data; the original 0.05 and 0.3 float bits and raw queue fields are checked. Host tessellation is checked for correct centres/radius within a stated tolerance. This is not exhaustive PPC/VMX special-value, hardware estimate, NaN, rounding or original sphere-tessellation certification.

## Finite checks and controls

There are 57 reset checks and 120 contact checks (three classifications × four flag combinations × ten checks). Enabled cases require one red wall or green curb triangle, three unshifted spheres of radius 0.3, events `[22,13,13,13]` with payload sizes `[40,20,20,20]`, and no submission before replay. Actual immediate replay must produce 1,299 CPU vertices in batches `[3,999,297]`, preserve colour/UV and state order, then leave both event queues empty with balanced ownership and no assert/unexpected primitive.

The immutable original controls contain exact C001/C002 source slices from `6502d531b5c33d7f1a0e26e5a2e5a1c005df87a6` and `11cbd50c824724c49d425fc91793ba2453bba320`, plus raw source hashes and Git blob IDs. They intentionally use the candidate's same production downstream providers to isolate these two changes. They are not complete old-revision builds. Both must compile, execute 177 checks, fail exactly the 57 reset checks and eight checks in each of four enabled contact cases (89 failures), and exit 1. Compile/link failure, missing labels, broad nonzero exit or a fabricated draw fallback cannot satisfy a control.

Execution is restricted to the genuine GitHub-hosted Windows2022 x64 / Jobs4 candidate workflow. The entire Python worker and its compiler/linker/test descendants run inside the unchanged owned Windows Job helper; receipts are joined again after zero active processes and closed handles. No local test evaluation is part of this proposal.
